# v2.6.0 架构链路审计（Layer A/B 接线核查）

> 基线：v2.6.0（commit 3edd7fa）。核查对象：新能力的每一环是否真正接通——
> 「类存在、测试通过、但组合根没注入」式断联；以及功能声称与实际行为的偏差。
> 全部条目逐行读源码确认。

---

## W1. ★ Layer B 名为流式，实为「攒完再发」

> **✅ v2.7.0 已修复**：`core/stream_reply.py` 重写为真·流式——`stream_reply_turn` 在 `guarded_stream` 每刷出一段时**立即发送**，收尾只补记账；`handle_stream_reply` 返回 `(reply, memory_update, handled)` 三态。另外「已发出部分段后异常」只补记账、不降级重发整轮（避免重复刷屏）。测试：`test_segments_sent_immediately_in_order`、`test_partial_send_does_not_re_fall_back`。

**链路**：router(400-407) → collect_stream_segments → guarded_stream → chat_stream → SSE 增量
→ router 拿到完整段列表 → （查重/表情包）→ _send_reply → plan → send_plan 逐条发。

**证据**：`src/core/stream_reply.py:14-33` 把所有 chunk extend 进一个 list 才返回；router 在流式结束后才进入发送分支。**全程没有任何「段到了就先发」的回调出口**。

**后果**：用户看到的行为 = 整轮生成完毕后再按句分段发出，与 Layer A 在感官上无差别。流式省下的「首句早到时间」被完全丢弃（再叠加 C5 的 1.5~4 秒段间隔）。**这是与 dsh-qq-bridge 流式效果的最大偏差。**

**方案**：collect_stream_segments 增加逐段回调（on_segment: 每刷出一段立即发送），收尾时只补发尾部；同时 send 路径要接 C1 的 plan 级计数与 C5 的零间隔。涉及发送、记账、查重三处的时序重构——改动比 C1 大，建议单列任务。

## W2. guarded_stream 绕过 guarded_chat 的熔断 / 人格 / 知识注入链

> **✅ v2.7.0 已修复**：把 `guarded_chat` 的注入段抽成 `_enrich_base_kwargs`（人格 + 管理员补充规则 + 群梗）与 `_enrich_attempt_kwargs`（自定义 prompt + 花语记忆 + 群昵称 + 群风格规则），`guarded_stream` 与 `guarded_chat` 共用；并补齐 provider / 群级熔断的准入与成功/失败回写。

**证据**：`src/core/ai_gateway.py:98-115`（guarded_stream 仅 _ai_allowed 预算闸 + chat_stream 循环）；对照 guarded_chat 完整链路：
- 熔断准入 provider_breaker.allow()（:132）+ 群级 breaker；
- 人格解析 persona_manager.resolve_persona（:161）；
- 群聊梗注入 meme_manager.build_context_block（:175）；
- 花语记忆检索 blossom_memory.search（:187 附近）；
- 群昵称 / 群风格规则（:198-209）。

**后果**：STREAM_REPLY_ENABLED=true 时，模型收到的 system prompt **没有人设、没有本群梗、没有花语记忆、没有群昵称风格**——花璃的所有「群聊人格」能力在流式模式下全部断电；同时熔断器不计流式的成败（record_success/failure 未调用，监控与熔断全盲）。

**方案**：guarded_stream 复用 guarded_chat 的请求前置（proposal：把 guarded_chat 的「组装 kwargs」段抽成 _prepare_chat_kwargs 共用方法），并补熔断准入与成功/失败回写。

## W3. 流式成功时 memory_update 恒为 None（记忆链断联）

> **✅ v2.7.0 已修复**：`StreamOutcome` 携带 `memory_update`，`handle_stream_reply` 原样返回给 router，`apply_memory_update` 恢复接线。与 C4 同源、合并实施。

**证据**：chat_stream 无返回值；router:407 拿到的只有段列表；`apply_memory_update(...)`（router:415-417）收到 memory_update=None 空转。

**后果**：流式模式下 MEMORY_JSON 行不被剥离（直接作为消息发出，内容泄漏观感差）且记忆不写入。与 C4 同源，独立列出因为这是**链路断联**（返回值通道缺失）而非单纯策略问题。

**方案**：collect_stream_segments 返回 (segments, memory_update)，内部跑 parse 逻辑（与 C4 方案合并实施）。

## W4. 流式空产出 → 触发一次额外的整轮请求（双倍预算）

> **✅ v2.7.0 已修复**：三态 `STREAM_OK / STREAM_EMPTY / STREAM_ERROR`——成功但空产出走兜底（@场景「喵？」），**不再**发起第二次完整请求；只有「未发出任何段且异常」才降级。测试：`test_empty_stream_mentioned_gets_fallback_reply`、`test_error_before_any_send_falls_back`。

**证据**：router:400-407：collect 返回 None 时 reply 保持 None，随后 `if reply is None: guarded_chat(...)` 照常执行。

**后果**：流式成功但模型输出为空（或只被句子缓冲丢弃的纯空白输出）时，**再跑一遍完整 guarded_chat**：单条用户消息消耗 2 次真实 API 预算，且语义上把「空回复」当成了「流式失败」。

**方案**：区分三种结果——流式异常（降级）、流式成功但空（走兜底「喵？」）、流式成功有段（直接发送）。collect_stream_segments 用哨兵值或异常类型区分，router 按 OK/EMPTY/ERROR 三分支处理。

## W5. 预算双重扣减（流式失败 + 降级重试）

> **✅ v2.7.0 已修复**：新增 `BudgetManager.refund()`（全局/群级计数各回退一次 + 恢复 check() 前的用户限速时间戳），`guarded_stream` 异常分支调用它再抛错，降级路径只扣一次。

**证据**：guarded_stream 每次调用先 _ai_allowed 扣预算；降级路径guarded_chat 的 attempts 循环每个 attempt 再扣。

**后果**：流式失败后降级，单轮对话扣 2+ 次预算。与「一次预算 = 一次真实 API 尝试」的语义注释相悖（重试语境成立，流式降级语境是额外惩罚）。

**方案**：guarded_stream 失败时回退本次扣减，或降级路径的首个 attempt 不再重复扣（把流式消耗计入 attempt 0）。

## W6. 一致性门禁盲区：split_reply 不在 _SENDER_ACTIONS

> **✅ v2.7.0 已修复**：`manager._LOCAL_ACTIONS` 本地动作表（split_reply / split_message / merge_message）与 `permissions` 逐条对账，新增测试 `test_local_actions_have_permissions`；删映射或改了声明都会报红。

**证据**：`tests/test_api_consistency.py` 的四向一致性只校验 _SENDER_ACTIONS ↔ permissions ↔ Sender ↔ 引用；split_reply 走 _ext_msg_friend 分支，不在动作表。

**后果**：`split_reply` 的权限映射（permissions.py:192）**没有自动校验防线**——将来有人删映射、或加新本地动作忘了登记，四向门禁不会报红。

**方案**：把 _ext_msg_friend / _ext_ai 等本地动作分支也纳入一致性校验（或单独加一张 LOCAL_ACTIONS 表与 permissions 对账测试）。

## W8. 插件 SDK 副本未同步

> **✅ v2.7.0 已处理**：新增测试 `test_plugin_fixture_sdk_methods_subset`——插件夹具副本的公开方法必须是本体子集（允许副本缺新方法，禁止出现本体没有的幻影 API）。副本的完整同步仍归插件作者维护。

**证据**：`plugin_sdk/flowerie_sdk/bot.py` 新增 split_reply；`tests/plugins/*/flowerie_sdk/bot.py`（gap_echo 等插件自带副本）未含。

**后果**：仓库内副本分散，若插件复制旧副本分发，split_reply 不可用。docs 说 SDK 副本随插件分发，无自动一致性保证。

**方案**：不管（副本归插件作者维护），或加一个测试断言「插件夹具副本的 Bot 公开方法是本体的子集」。
