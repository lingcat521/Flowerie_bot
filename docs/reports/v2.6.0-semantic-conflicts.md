## C1. 冷却 / 连续回复计数 × 分段发送

> **✅ v2.7.0 已修复**：`ReplyPlan.count_as_one` 标记整轮分段为一次逻辑发言，`reply_dispatch.after_sent` 只在首条记一次（连续回复/上下文/最近回复），上下文记合并文本一条；`SplitSegments` 来源由 `plan_from_config` 识别。AI 自主多条（MULTI_REPLY）保持按条计数。测试：`test_reply_splitter.py::test_split_segments_count_as_one_and_no_interval`、`test_reply_stream.py::test_records_one_turn_with_merged_text`。

**证据**：`src/core/reply_dispatch.py:30-43`（after_sent 每发一条计一次 record_bot_reply + add_context + add_recent_reply）；`src/core/cooldown_manager.py:46-56`（consecutive_replies >= MAX_CONSECUTIVE_REPLIES(3) → block 60s）。

**后果**：分段回复不受发送通道阻拦（send_plan 中途不检查冷却），但第 3 段发完后群被静默 60 秒——**用户下一句话被吞**。同时每段各自进上下文历史，AI 下轮看到的是碎片「半句 半句」。

**方案（推荐）**：把「一轮分段回复」定义为一次逻辑发言——record_bot_reply 在 plan 级只计一次、上下文记录合并文本一条、BOT_COOLDOWN 基准取 plan 开始时刻。仅改分段/流式路径，AI 自主多条（MULTI_REPLY）保持按条计数（其代码注释明说这是刻意设计）。

## C2. SPLIT_REPLY 段长上限默认 40 = MAX_REPLY_LENGTH，叠加人设 15~20 字

> **✅ v2.7.0 已修复**：`SPLIT_REPLY_SEGMENT_LIMIT` 默认改为 **200**；`prompt_builder._split_reply_hint` 在 SPLIT 开启时注入「最多 N 段、每段不超过 M 字、用换行分段」提示，使模型输出与切分上限对齐（人设短聊风格在开关关闭时零变化）。

**证据**：`src/config.py:121-125`（SPLIT_REPLY_SEGMENT_LIMIT 默认 40）；`src/services/prompt_builder.py:26-32`（人设强制「回复尽量在 15～20 字以内」）。

**后果**：默认配置下模型输出几乎都 < 40 字，**切分功能事实休眠**；即使触发，85 字日记被切成 40/40/5，段尾仍是硬切观感。开关语义模糊：用户开了 SPLIT 却看不到 dsh 那种「按行成段」的效果。

**方案**：SPLIT_REPLY_SEGMENT_LIMIT 默认改为 200，并把 prompt_builder 里的每条字数提示改为读 SPLIT 段长，使模型输出与切分上限一致。需你确认是否允许模型输出变长（与人设短聊风格相悖）。

## C3. MULTI_REPLY 的 AI 多条上限被 SPLIT 开关接管

> **✅ v2.7.0 已修复**：新增 `SplitSegments(list)` 标记类，`plan_from_config` 按来源分流——切分段/流式段用 `SPLIT_REPLY_MAX_MESSAGES`，AI 多条用 `MULTI_REPLY_MAX_MESSAGES`，互不接管。测试：`test_split_segments_use_own_max_messages_not_multi_reply_cap`。

**证据**：`src/core/reply_plan.py:119-124`——`if SPLIT_REPLY_ENABLED: return plan.clamped(SPLIT_REPLY_MAX_MESSAGES)`，优先于 MULTI_REPLY 的 clamped(3)。

**后果**：两开关同开时，模型输出的 {"messages": [...]} 多条回复上限从 MULTI_REPLY_MAX_MESSAGES(3) 变成 SPLIT_REPLY_MAX_MESSAGES(8)——**AI 无权绕过的防刷屏上限被无意放宽**，与 guarded 层「AI 无权绕过上限」注释相悖。

**方案**：plan_from_config 区分来源——切分段与 AI 多条分别按各自上限 clamp。可用 SplitSegments 轻量标记类（list 子类）区分，不破坏既有 isinstance(list) 消费者。

## C4. 流式路径完全绕过 parse_reply_content

> **✅ v2.7.0 已修复**：抽出 `reply_parser.split_memory_lines`（与 `parse_reply_content` 同一套识别规则），流式逐段剥离记忆行；`handle_stream_reply` 返回 `memory_update` 交给 `apply_memory_update` 照常落库。测试：`test_memory_json_line_never_sent`、`test_chinese_memory_prefix_stripped`。

**证据**：`src/core/message_router.py:400-407`（段列表直接成为 reply）；非流式路径经 `reply_parser.parse_reply_content` 剥离 MEMORY_JSON 行并提取 memory_update；chat_stream 不返回 memory_update。

**后果**：
1. 模型输出 MEMORY_JSON 行时，流式路径不剥离，**直接作为消息文本发给用户**；
2. 流式成功时 memory_update 恒为 None——**长期记忆在流式模式下失效**；
3. AI 多条 JSON 同理不被解析。

**方案**：collect_stream_segments 结束后对段集合跑一次轻量后处理（合并文本 → 剥记忆行/多条 JSON → 返回 (segments, memory_update)），与非流式路径语义对齐。

## C5. 流式分段被 ReplyPlan 的间隔延迟消解「及时性」

> **✅ v2.7.0 已修复**：新增 `SPLIT_REPLY_INTERVAL_MODE`（默认 `none` = 立即发送），仅作用于切分/流式段；`MULTI_REPLY_INTERVAL_MODE` 仍管 AI 自主多条。非法值回退 `none`。测试：`test_split_segments_count_as_one_and_no_interval`、`test_split_segments_invalid_interval_mode_falls_back_none`。

**证据**：`src/core/reply_plan.py:117`（ReplyPlan.of 继承 MULTI_REPLY_INTERVAL_MODE，默认 random 1.5~4 秒）；流式段经 _send_reply → plan_from_config → send_plan。

**后果**：流式段发送时每段仍等 1.5~4 秒——8 段回复完整送达需 12~32 秒，**流式「边生成边看到」的价值被清零**（且当前实现本来就是攒完再发，见链路审计 W1）。

**方案**：流式/切分来源的 plan 用 INTERVAL_NONE（立即发送），random 间隔留给 AI 自主多条；或新增 SPLIT_REPLY_INTERVAL_MODE 独立配置。

## C6. 查重 / 表情包只看首段

> **✅ v2.7.0 已修复**：流式路径改为**逐段**查重与表情包识别（`stream_reply._process_segment`），`[STICKER:]` 出现在任意段都能识别；最近回复只记整轮合并文本一条。测试：`test_sticker_only_segment_sent_as_image`、`test_duplicate_segment_skipped_but_new_one_sent`。

**证据**：`src/core/message_router.py:430-443` 全部使用 first_text(reply)（取 list 首段）。

**后果**：
1. [STICKER:文件名] 标记若出现在第 2、3 段 → 提取不到 → **标记字符作为正文发给用户**；
2. is_duplicate_reply 只拿首段比对，后续段无查重；
3. add_recent_reply 每段一条（after_sent），相邻段污染查重集。

**方案**：list 回复的查重/表情包提取改为在合并文本上做；recent_reply 每轮记一条合并文本（与 C1 一并改）。

## C7. sender 二次截断（STREAM 开 + SPLIT 关）

> **✅ v2.7.0 已修复**：`Sender._reply_limit()` 增加 STREAM 感知——`STREAM_REPLY_ENABLED=true` 时取 `STREAM_REPLY_MAX_FLUSH`，流式段不再被按 40 二次腰斩。

**证据**：`src/services/sender.py:125-131`（_reply_limit 只认 SPLIT_REPLY_ENABLED）；流式段最长 MAX_FLUSH=200（`src/services/ai_streaming.py`）。

**后果**：只开 STREAM 时，流式刷出的段最长 200，发送时被 sender 按 MAX_REPLY_LENGTH(40) 再砍——**流式分段被二次腰斩**且段尾带「...」，与流式初衷相悖。

**方案**：_reply_limit 增加 STREAM 感知（流式段在段长上限内不截），或流式路径整段直发不经 sender 截断分支。

## C8. reply_parser 注释仍引用已弃用任务书

> **✅ v2.7.0 已修复**：`reply_parser.extract_multi_messages` 与 `ai_client.extract_multi_messages` 的注释改为「多条结构只认完整 JSON；换行/标点切分见 reply_splitter（Layer A）」，决策脉络保留、不再引用已弃用的任务书。

**证据**：`src/services/reply_parser.py` 注释「不做换行/标点猜测 —— 任务书 §6 明确要求」；`src/services/ai_client.py` 的 extract_multi_messages 同款注释。

**后果**：文档与现行设计矛盾（v2.6.0 已引入标点/换行切分），后读者会被误导。

**方案**：注释更新为「多条结构只认完整 JSON；换行/标点切分见 reply_splitter（v2.6.0 Layer A）」，保留决策脉络不删历史。
