# v2.8.0 每日群聊摘要（设计评估与落地记录）

> 本文记录「每日凌晨群聊摘要」的设计来源、移植决策与覆盖范围。
> 时间：2026-10-23；对应 commit 923a6ee；功能开关 `DIGEST_ENABLED`（默认关）。

---

## 一、设计来源

功能移植自 DeepSeek Harness 的会话压缩模块（dsh-compaction-basic 0.2.1-rc.2）。
评估了「整体移植 vs 摘要层移植」后选择后者：DSH 的事件日志 + surface 双层架构
属于其内核地基，Flowerie 的状态层（deque + 策略引擎）建立在不同语义上，
整体移植等于重写状态层，收益不匹配风险。

## 二、借来的三样核心设计

- **嵌套合并（PRIOR checkpoint）**：已有摘要作为既往 checkpoint 传入并 merge，
  而非照抄。上下文里永远只有一份摘要——这是连续运行几个月不堆叠、不爆膨的根本。
- **既定背景 preamble**：摘要前加「Treat the captured context as established
  background and build on it without restating it」，模型把摘要当背景而非
  要复述的稿子（少这句模型会变成「背摘要机器」）。
- **收敛检查**：摘要不得比被压缩的原文还长，否则拒写（防爆膨护栏）。

## 三、超越 DSH 的两处（群聊场景必须）

- **压缩频率控制**：DSH 的编程会话按 token 压力触发（0.8 阈值），群聊活跃群
  会变成每 30 分钟一次、一天 48 次 LLM 调用。Flowerie 改为定点触发（默认
  00:00），成本固定为「每活跃群每天一次」，且跑在夜间静默期。
- **原始消息归档**：DSH 靠事件日志保留可回放历史。Flowerie 的缓冲是有界
  deque，摘要失败时保留缓冲下轮重试，已成功摘要写入 SQLite 持久化。

## 四、数据流（工作上下文与摘要数据源分家）

```
消息进群 ──> ContextManager.add_context ──> GroupState.context（工作 deque）
                │
                └──> digest_feed ──> DailyDigestService 缓冲（每群 1000 条）

00:00 ──> 缓冲够量？──> 一次 AI 调用（含旧摘要 merge）──> 收敛检查
                │                                        │
                └─ 不够则跳过                      落地三处：
                                                1) deque 独立 checkpoint（标记条目）
                                                2) SQLite 持久化（重启恢复）
                                                3) DIGEST_EXPORT_DIR 的 txt
```

## 五、覆盖范围与已知边界

- 覆盖：群聊文本消息（用户消息 + 花璃自己的回复）
- 不覆盖：图片 / 戳戳 / 表情包索引等非文本交互（不在摘要数据源内）
- 已知边界：
  - 缓冲为内存态，重启丢失**当天**缓冲（已生成的摘要不丢，SQLite 持久化）
  - 本机回环模型（Ollama / vLLM 等）同样可用作摘要模型
  - 摘要调用计入共享 AI 预算，不绕过三层预算

## 六、集成暗坑（已覆盖测试）

**摘要条目不得污染主动聊天概率窗口**：`should_reply_by_context` 读
`context[-5:]`，若摘要条目（is_bot）混入会在 digest 后的安静群把「近 5 条
全是机器人」误判为「没有真人发言」→ 返回 False → 主动聊天被掐死。
对策：摘要条目独立于 deque（`GroupState.digest_checkpoint` 属性），
扫描路径完全不接触。`tests/test_daily_digest.py` 有专门覆盖。
