# 性能基线（树莓派可行性评估）

> 对应 **v2.19.3**。本文回答一个问题：**花璃能不能跑在树莓派上，开销多大。**

## 先跑一遍

```bash
# 微基准：单次操作多快
python3 scripts/bench.py          # 全部用例
python3 scripts/bench.py --quick  # 快速版（迭代减半）
python3 scripts/bench.py --json   # JSON 输出，便于跨机器对比

# 负载基准：多群 + 附件并发能扛多少
python3 scripts/bench_load.py               # 五档全跑（约 1 分钟）
python3 scripts/bench_load.py --tier 3      # 只跑第 3 档
python3 scripts/bench_load.py --json

# 全功能压测：所有子系统同时跑
python3 scripts/bench_stress.py          # 三档（约 90 秒）
python3 scripts/bench_stress.py --tier 3 # 只跑极限档

# 资源占用：CPU/内存/磁盘 IO/文件描述符
python3 scripts/bench_resources.py
```

脚本只测**纯本地计算**（不含网络与 LLM），这样换机器才有可比性。

## 参考实测（Android 手机，Dimensity 700）

测试机：MT6833V/ZA（2×Cortex-A76 @2.2GHz + 6×Cortex-A55 @2.0GHz），8 核，Python 3.14.8。

| 用例 | p50 | p95 | 吞吐 | 峰值内存 |
| :--- | ---: | ---: | ---: | ---: |
| 分句 · 短句(18字) | 0.019 ms | 0.022 ms | 48,876 ops/s | 5 KB |
| 分句 · 中句(160字) | 0.046 ms | 0.064 ms | 21,040 ops/s | 6 KB |
| 分句 · 长句(1600字) | 1.194 ms | 1.252 ms | 834 ops/s | 19 KB |
| 表情标记提取 | 0.025 ms | 0.027 ms | 38,154 ops/s | 5 KB |
| 不可信文本消毒(1KB) | 0.095 ms | 0.107 ms | 10,276 ops/s | 5 KB |
| @ 检测（命中/未命中） | 0.003 ms | 0.004 ms | ~350,000 ops/s | 3 KB |
| 重复检测 · 单次 | 0.067 ms | 0.094 ms | 14,249 ops/s | 7 KB |
| SQLite 写入(100B) | 3.406 ms | 4.666 ms | 300 ops/s | 7 KB |
| SQLite 批量写 100 行 | 5.289 ms | 8.972 ms | 190 ops/s | 15 KB |
| SQLite 按主键读(1000 行库) | 0.352 ms | 0.455 ms | 2,823 ops/s | 122 KB |
| 解析 txt(35KB) | 5.831 ms | 7.489 ms | 170 ops/s | 84 KB |
| 解析 csv(500 行) | 7.125 ms | 9.512 ms | 136 ops/s | 79 KB |
| 面板页渲染(50 块正文) | 4.545 ms | 7.121 ms | 203 ops/s | 167 KB |
| 遍历 SCHEMA(256 键) | 0.088 ms | 0.092 ms | 11,170 ops/s | 4 KB |
| **本地处理链**（@检测→消毒→分句） | **0.128 ms** | 0.157 ms | 7,574 ops/s | 6 KB |

**整体内存**：进程 RSS **85 MB**（导入 12 个核心模块后增量 +15 MB）。

---

## 关键结论：本地开销可以忽略

一条群消息的本地处理链（@ 检测 → 消毒 → 分句）**0.128 毫秒**。

而一次 LLM 往返通常要 **1000~5000 毫秒**。也就是说：

```
总延迟 ≈ 10 ms（网络收发） + 1500 ms（LLM） + 0.13 ms（花璃本地）
                                    ↑ 占 0.009%
```

**本地处理再慢 20 倍，也才刚刚到 2.5 毫秒 —— 感知不到。**

负载视角同样宽松：10 群 50 msg/s 只用到 6% 单核（见下方负载基准）。
这是树莓派能跑的根本原因：花璃不是计算密集型，它是 IO 等待型（等 API 返回）。

## 负载基准（多群 + 附件并发）

微基准（上一节）测「单次多快」，但真实压力来自**并发**。用 `scripts/bench_load.py`：

```bash
python3 scripts/bench_load.py                # 全部五档
python3 scripts/bench_load.py --tier 3       # 只跑第 3 档
python3 scripts/bench_load.py --duration 20  # 每档 20 秒
python3 scripts/bench_load.py --json         # JSON 输出
```

每档模拟 N 个群各自按速率发消息，并按概率触发附件负载：
文件解析（`FileParser.parse_document` 真跑）、图片（GIF→首帧 PNG 真跑）、插件往返。

### 五档实测（Android / Dimensity 700）

| 档位 | 群数×速率 | 附件概率 | 实际吞吐 | p95 | CPU(单核当量) | RSS |
| :--- | :--- | :--- | ---: | ---: | ---: | ---: |
| 轻载 | 1×1/s | 无 | 1.0 msg/s | 15.5 ms | 0% | 70 MB |
| 日常 | 5×2/s | 文件2% 图5% 插件2% | 10.0 msg/s | 3.5 ms | 1% | 70 MB |
| 繁忙 | 10×5/s | 文件5% 图10% 插件5% | 49.6 msg/s | 6.6 ms | 6% | 70 MB |
| 压力 | 30×10/s | 文件10% 图20% 插件10% | 294.4 msg/s | 8.3 ms | 46% | 71 MB |
| 极限 | 50×20/s | 文件10% 图25% 插件10% | 947.2 msg/s | 11.3 ms | 78% | 71 MB |

> CPU 是 `process_time / wall_time` 的「单核当量」。Python 有 GIL，
> 主处理链实际跑在单核上，所以 78% 已经接近这个进程的单核极限。

### 三个结论

**① 真实场景离极限很远**

10 个群最繁忙时也就 10~20 msg/s（受 LLM 往返限制，每个群同一时刻通常只有 1 个请求在等）。
实测 50 msg/s 只用了 **6% CPU**，余量超过 15 倍。

**② 内存是平的**

从 1 群到 50 群、从 1 msg/s 到 947 msg/s，RSS 一直在 **70~71 MB**。
没有泄漏、没有随负载膨胀——因为消息处理是「进来→处理→丢弃」的无状态流水线。

**③ 附件才是真负载**

对比档位 3 与 5：

```
档位3:  50 msg/s,  附件 20%  → CPU  6%
档位5: 947 msg/s,  附件 45%  → CPU 78%
```

纯文本消息几乎不耗 CPU；文件解析（5-7 ms/次）和图片转码（GIF 解码 + PNG 编码）
才是成本大头。所以调优优先级是：**限制附件频率 > 优化文本链**。

### 树莓派折算（负载视角）

| 机型 | 单核相对 | 纯文本吞吐 | 10 群实际负载(50 msg/s) |
| :--- | ---: | ---: | :--- |
| Pi 5 | ~1.1× | ~1000 msg/s | CPU 约 5% |
| Pi 4 | ~0.55× | ~500 msg/s | CPU 约 11% |
| Pi 3B+ | ~0.25× | ~240 msg/s | CPU 约 25% |
| Pi Zero 2 W | ~0.15× | ~140 msg/s | CPU 约 35%（但内存吃紧） |

**即使 Pi 3B+，10 群场景也只用到四分之一单核。** 瓶颈从来不是 CPU。

> ⚠️ **必须装 64 位系统**：Python 3.14 预留 10+ GB 虚拟地址空间，
> 32 位 OS 的 4 GB 地址空间会让解释器起不来。

## 全功能极限压测（所有子系统同时跑）

前面测的是「某个功能多快」，这里测「**全都开着**会不会崩」。用 `scripts/bench_stress.py`：

```bash
python3 scripts/bench_stress.py              # 三档（约 90 秒）
python3 scripts/bench_stress.py --tier 3     # 只跑极限档
python3 scripts/bench_stress.py --json
```

同时运转的 9 个子系统：消息链 / 文档解析 / 图片转码 / UI 渲染 / SQLite /
记忆写入 / 表情索引 / 插件往返 / 摘要拼装。每一路按各自节奏全速跑。

### 三档结果

| 档位 | 并发 | 总吞吐 | 错误 | CPU | RSS 峰值 |
| :--- | :--- | ---: | ---: | ---: | ---: |
| x1 | 1 路 | 743 ops/s | **0** | 67% | 74 MB |
| x3 | 3 路 | 1080 ops/s | **0** | 74% | 74 MB |
| x6（极限） | 6 路 | 1138 ops/s | **0** | 70% | 75 MB |

### 极限档各子系统（x6）

| 子系统 | 吞吐 | p50 | p95 |
| :--- | ---: | ---: | ---: |
| 消息链 | 144.8/s | 0.33 ms | 0.45 ms |
| 文档解析 | 156.8/s | 0.29 ms | **158.95 ms** |
| 图片转码 | 124.6/s | 1.59 ms | 2.73 ms |
| UI 渲染 | 124.6/s | 3.25 ms | 6.37 ms |
| SQLite | 289.5/s | 0.62 ms | 1.34 ms |
| 表情索引 | 105.1/s | 0.00 ms | 0.01 ms |
| 插件往返 | 124.6/s | 0.16 ms | 0.22 ms |
| 摘要拼装 | 68.1/s | 0.16 ms | 0.46 ms |

### 四个结论

**① 没崩，0 错误**

三档合计 76,000+ 次操作，**零错误**。SQLite 并发写没有 database is locked，
asyncio 没有 event loop 阻塞告警。

**② 内存几乎不涨**

```
x1: 72 -> 73 MB
x3: 73 -> 74 MB
x6: 74 -> 75 MB   <- 6 倍并发只涨 1 MB
```

**③ 瓶颈是单核（GIL），不是内存**

并发从 3 路加到 6 路，吞吐只从 1080 涨到 1138（+5%），CPU 停在 70%。
典型的**单核饱和**：Python 的 GIL 让所有 CPU 密集型工作排在一个核上。

**④ 文档解析最先排到队**

全功能 x1 时文档解析 p95 = 16 ms，x3 = 74 ms，x6 = **159 ms** —— 延迟涨 10 倍，
吞吐只从 101 涨到 157（+55%）。

这是**队列饱和**的教科书特征：请求开始排队，每条变慢，总量上不去。
真要提吞吐只能上进程池（绕开 GIL）。

> 但真实场景不需要：一个群同时来 6 份文档的概率极低，
> 而且文件解析已限制 10MB + 8000 字符截断。

### 树莓派折算（全功能极限）

| 机型 | 单核相对 | 极限吞吐 | 10 群真实负载 |
| :--- | ---: | ---: | :--- |
| Pi 5 | ~1.1x | ~1250 ops/s | CPU <10% |
| Pi 4 | ~0.55x | ~620 ops/s | CPU <20% |
| Pi 3B+ | ~0.25x | ~285 ops/s | CPU <35% |

**即使 Pi 3B+，全功能同时开也只用到三分之一单核。**

## 除了 CPU 和内存，还吃什么（资源谱系）

上线前最容易被忽略的维度。用 `scripts/bench_resources.py` 实测：

```bash
python3 scripts/bench_resources.py            # 混合负载 15s + 采样
python3 scripts/bench_resources.py --idle 10  # 额外测空闲 10s
```

### 实测结果

| 维度 | 实测值 | 评价 |
| :--- | ---: | :--- |
| CPU（单核当量） | 42% | 混合负载下 |
| 内存 RSS | 71 MB | 常驻 |
| 内存 VMS（虚拟） | **10,850 MB** | ⚠️ 见下方说明 |
| 线程数 | 2 | 很少 |
| 文件描述符 | 11 | 很少（默认 ulimit 1024+） |
| 磁盘写入（混合负载） | 1.06 MB/s | 压测值，非真实 |
| 磁盘写入（真实速率） | **25.8 KB/条消息** | 见下方换算 |
| 数据目录 | 342 MB | 其中 343 MB 是表情包 |

### VMS 10 GB 是假象

```
空 Python 进程 VmSize:  10,830 MB
导入全部模块后:         11,074 MB   ← 只涨 244 MB
实际 RSS:                   71 MB   ← 才是真占用
```

Python 3.14 在 64 位系统上会预留极大的虚拟地址空间（arena 分配策略），
**这不是内存占用**。判断依据：RSS 才 71 MB。

影响：
- **64 位系统**（Pi 4/5 的 64 位 OS）：完全无影响
- **32 位系统**（Pi 3 装 32 位 OS）：地址空间只有 4 GB，**可能起不来** → 必须用 64 位

### 磁盘写入：SD 卡寿命实测

真实速率（1 条消息 / 3 秒 = 20 msg/min，10 群较繁忙时的水平）：

```
物理写入 25.8 KB / 条消息
```

换算：

| 场景 | 每天 | 每年 |
| :--- | ---: | ---: |
| 全天 24h 满载 | 726 MB | 259 GB |
| 每天活跃 8h | 242 MB | 86 GB |

**SD 卡寿命**（128GB TLC，写入放大 2x，标称 100 TBW）：

| 场景 | 年写入量 | 寿命 |
| :--- | ---: | ---: |
| 全天 24h | 0.51 TB/年 | **约 198 年** |
| 每天 8h | 0.17 TB/年 | **约 594 年** |

即使按 3 倍保守估算（配置写入 + 画像 + 知识库 + 日志），也是**几十年**。

**结论：SD 卡不会因为写入量写坏。** 真正的问题是**写入延迟**，不是寿命。

### 但 synchronous=FULL 在 SD 卡上会很慢

花璃默认：

```sqlite
journal_mode = wal      -- 好，支持并发读
synchronous = 2 (FULL)  -- 每次都 fsync，最安全但最慢
```

在内存盘上单写 3.4 ms。换到 SD 卡可能变 **50~200 ms**（每次 commit 都要等物理刷盘）。

**建议**（只在树莓派这类慢盘上）：

```sql
PRAGMA synchronous = NORMAL;
```

WAL + NORMAL 的组合下，崩溃最多丢最后几条事务，但不会损坏数据库。
换来的是写入延迟从百毫秒降到个位数。

### 空闲时不写盘

实测：静置 5 秒，磁盘写入 **0.00 MB**，write 系统调用 **0 次**。

没有心跳写盘、没有定时刷状态。只有真实活动才产生 IO。

### 网络

不是资源大头：

| 操作 | 数据量 |
| :--- | ---: |
| 一次 LLM 对话（含上下文） | 5~50 KB |
| 搜索结果 | 2~10 KB |
| 图片 base64 上传 | 100 KB ~ 1 MB |

按 20 msg/min 算，峰值带宽 **几 KB/s**，任何网络都够。

## 各代树莓派估算

按上表实测值，以 Cortex-A76（测试机大核）为基准折算。树莓派单核性能大致是它的：

| 机型 | CPU | 单核相对性能 | 本地处理链 p50 | 判断 |
| :--- | :--- | ---: | ---: | :--- |
| **Pi 5** | Cortex-A76 @2.4GHz | ~1.1× | ~0.12 ms | ✅ 毫无压力 |
| **Pi 4** | Cortex-A72 @1.5GHz | ~0.55× | ~0.23 ms | ✅ 完全够用 |
| **Pi 3B+** | Cortex-A53 @1.4GHz | ~0.25× | ~0.51 ms | ⚠️ 能用，但内存吃紧 |
| Pi Zero 2 W | Cortex-A53 @1GHz | ~0.15× | ~0.85 ms | ⚠️ 单条能跑，并发悬 |
| Pi Zero W | ARM11 @1GHz | ~0.03× | ~4 ms | ❌ 不建议（512MB 内存也不够） |

> 折算只是量级参考。真实差异受内存带宽、SD 卡 IO、Python 版本影响，
> 拿到机器后请自己跑一次 `python3 scripts/bench.py --json` 对比。

## 内存是真正的门槛

性能不是问题，**内存才是**：

| 组件 | 常驻内存 |
| :--- | ---: |
| Python 进程 + 核心模块 | ~85 MB |
| SQLite（含记忆/画像/知识库增长） | 10~100 MB |
| 表情包索引（几千张的元数据） | 5~30 MB |
| 插件进程（每个独立进程） | 20~50 MB/个 |
| **典型总计** | **150~300 MB** |

| 机型 | 内存 | 结论 |
| :--- | ---: | :--- |
| Pi 5 / Pi 4 (4GB·8GB) | 4–8 GB | ✅ 充裕 |
| Pi 4 (2GB) | 2 GB | ✅ 够用 |
| Pi 3B+ (1GB) | 1 GB | ⚠️ 能跑，别装重插件 |
| Pi Zero 2 W (512MB) | 512 MB | ❌ 会 OOM |

## 其他注意事项

### SD 卡是最大隐患

SQLite 写入在测试机上是 **3.4 ms/次**（这已经是 DDR 内存的速度）。
换成 SD 卡（尤其 Class 10 低端卡）可能慢 10~50 倍，且寿命有限——
SQLite 频繁写会加速磨损。

**建议**：
- 用 **USB 3.0 SSD** 而非 SD 卡（Pi 4/5 支持 USB 启动）
- 或至少 A2 级 microSD
- 开启 SQLite WAL 模式（花璃已默认开启）

### 无头浏览器跑不了

`tests/e2e/` 需要 Chromium。树莓派上要通过 `apt install chromium-browser`
（Pi OS 有 ARM 版），能跑但很慢（单次 E2E 可能 30 秒+）。CI 里跑就行，本地可以 skip。

### NapCat / OneBot 端的开销

这部分**不在花璃进程内**，但同样占资源：
NapCat 是 Node.js，空载约 **150~250 MB**。所以：

```
树莓派总占用 ≈ 花璃 200 MB + NapCat 200 MB ≈ 400 MB
```

### 无 GPU 需求

花璃不跑本地模型，识图/搜索/对话全走 DeepSeek API。**GPU 完全不需要**，
Pi 5 的 VideoCore VII 闲着就闲着。

## 推荐配置

| 用途 | 推荐 |
| :--- | :--- |
| 1~3 个群，轻度使用 | **Pi 4 (2GB) + A2 microSD** |
| 5~10 个群 + 插件 + 表情包多 | **Pi 4 (4GB) 或 Pi 5 + USB SSD** |
| 多实例 | Pi 5 (8GB) + SSD |

**不推荐**：Pi Zero 系列（内存/IO 双重瓶颈）、Pi 3B+ 以下。

## 怎么在你自己的机器上对比

```bash
# 树莓派上
git clone <repo> && cd Flowerie_bot
python3 scripts/bench.py --json > pi.json

# 对比两台机器的结果
python3 - <<'EOF'
import json
a = json.load(open('pi.json')); b = json.load(open('phone.json'))
for ra, rb in zip(a['results'], b['results']):
    ratio = ra['p50'] / rb['p50'] if rb['p50'] else 0
    print(f"{ra['name']:<28} {ra['p50']:8.3f} vs {rb['p50']:8.3f} ms  ({ratio:.2f}x)")
EOF
```
